# Phase 3 修复候选：产品决策与最小方案

**状态：**产品口径已补充；修复方案待审核；未批准业务代码修改。
**范围：**仅 Bing tracking URL 图片收录，以及 Images Status 刷新、缓存与 429 处理。Word Count、CMLabs、评分权重及其他规则均不在本方案范围内。

## 1. Bing tracking URL

### 已确认的产品决策

仅排除精确追踪端点。解析图片 URL 后，主机名必须严格为 `bat.bing.com`，路径必须区分大小写且严格为 `/action/0`。允许任意 Query 参数；Fragment 不参与匹配。不得排除路径 `/action/0/`、大小写不同的路径或其他主机上的同路径；不得过滤整个 `bat.bing.com` 域名、所有第三方域名、普通带查询参数的图片 URL，也不得改变其他图片的采集、重复项保留或 Alt 检查规则。

### 最小实现候选

在图片扫描器现有排除条件处增加一个精确端点判断；仅影响图片清单中的该资源。计数与图片明细应遵循现有 excluded-image 口径，不另增通用追踪识别规则。Audit 图片 Alt 统计继续消费扫描器输出，不单独增加过滤分支。

## 2. Images Status 缓存与刷新

### 已确认的产品决策

- 最终取得的 HTTP 响应缓存 5 分钟；缓存包括现有 OK/Broken 判定覆盖的 4xx/5xx 响应，排除 429。普通页面重新打开时，在缓存仍有效且键匹配的情况下复用。
- 用户主动点击 Refresh 时强制重新检查本次筛选范围，不使用有效缓存跳过请求。
- 同一轮中相同图片 URL 只请求一次，结果应用到所有重复行。
- 同时最多 2 个状态请求，不为提速提高并发上限。
- 429 不自动重试；尊重有效的 `Retry-After`。无有效响应头时，按图片请求 URL 的 Origin 从收到 429 时起冷却 30 秒。冷却期间该图片请求 Origin 的手动 Refresh 不发请求；冷却结束后只允许用户手动刷新，不自动请求。其他图片请求 Origin 不受影响。
- 已成功取得的状态不得因同轮 429 或未完成请求被覆盖成失败/未检查；Refresh 期间若当前界面有旧状态，即使缓存已过期也保留为明确标记的“上次结果”，但不得将其当作有效缓存复用。没有旧状态的未完成项显示未检查。

### 建议明确的实现口径

**缓存键与作用域：**扩展会话内的缓存键是“发起状态检查的页面 Origin + 规范化图片请求 URL”；图片 URL 规范化时移除 fragment、保留 query。页面 Origin 纳入缓存键，是因为跨域/CORS 可使同一个图片 URL 在不同页面上下文中得到不同的可检查结果。缓存值至少包含 `{status, checkedAt, expiresAt, source, runId}`；`source` 区分本轮实时结果与历史缓存结果。**冷却键不同：**429 冷却仅按图片请求 URL 的 Origin 记录，不按页面 Origin；页面 Origin 与图片请求 Origin 可能不同，二者不得混用。

**什么结果可缓存：**最终取得可判定的 HTTP 响应时缓存 5 分钟，包括现有判定覆盖的 OK 与 Broken 状态及其 4xx/5xx 响应；429 不缓存。这里“失败结果不替代有效成功缓存”中的“失败”仅指没有取得可判定的最终 HTTP 响应，例如超时、网络错误、脚本权限失败、CORS 阻止或无响应状态码；这类失败不覆盖有效旧缓存。新取得的 404/500 是可判定的新响应，必须替换旧的 200 缓存。若 HEAD 返回 405/501 并回退 GET，只缓存 GET 的最终结果；GET 无法取得最终响应时不缓存 HEAD 的 405/501，也不缓存无响应结果。缓存 TTL 从取得最终响应时开始，读取缓存不延长 TTL。

**过期和清理：**到达 `expiresAt` 即视为过期，不展示为当前有效状态、不用于普通重开复用；读取和写入时惰性清理过期记录。页面快照最多可保留 10 分钟，但这不延长其中图片状态的 5 分钟 TTL。读取快照时必须逐项重新校验 `checkedAt/expiresAt`，仅恢复未过期的图片状态；旧快照中没有检查时间的 `imageStatuses` 一律视为不可验证/过期，不得直接显示为有效缓存。缓存只存在于 `chrome.storage.session`，浏览器重启、扩展重载/更新或会话存储清空后自然失效，不建立永久历史。容量限制触发时优先删除最早过期/最旧记录，不影响当前扫描数据。

**页面切换与普通重开：**Popup/工具页普通卸载、重开或工具切换不清空有效缓存。缓存按页面 Origin + 图片 URL 隔离，可在同一页面 Origin 下的页面重开时复用相同图片 URL 的有效结果；切换到不同页面 Origin 时不复用其状态检查结果。冷却状态另按图片请求 Origin 隔离。若扫描结果变化，只对新结果中的 URL 查找缓存；已移除图片不再显示，新 URL 无缓存则未检查。

**Rescan：**Rescan 创建新扫描代次并更新图片清单，但不主动清除仍在 5 分钟有效期内的状态缓存。新结果仅可为当前清单中、缓存键匹配且未过期的图片恢复状态；其来源显示为缓存。Rescan 期间旧代次的状态响应不得写入新扫描结果或新代次缓存。用户主动 Refresh 则绕过缓存，并以新实时结果更新该 URL 的缓存。

**429 冷却：**优先解析 `Retry-After` 的 delta-seconds 或 HTTP-date；冷却截止时间从收到 429 的时刻起算，使用有效头指定的截止时间。头缺失、无效或因 CORS 不可读取时，按图片请求 URL 的 Origin 冷却 **30 秒**。跨域 `fetch` 若被 CORS 完全阻止且未收到可见的 429 响应，则没有 429 证据，不得声称启动了 429 冷却；此时该请求属于未取得可判定响应。冷却只以图片请求 URL 的 Origin 为键，与缓存的“页面 Origin + 图片 URL”键不同。冷却状态保存在扩展会话内。冷却期间手动 Refresh 不向该 Origin 启动新请求；冷却到期后只允许再次手动刷新，不自动请求。

**429 与并发：**观察到某图片请求 Origin 的 429 后，不再启动该 Origin 的新请求；该 Origin 已经发出的并发请求允许完成，其最终响应按正常规则处理和缓存（若最终状态也是 429 则不缓存）。不同图片请求 Origin 的待处理任务仍可继续，且总并发不超过 2。多个并发请求同时返回 429 时，按各自图片请求 Origin 建立/更新冷却；同一 Origin 的冷却截止时间取所有适用截止时间中的较晚值：有效 `Retry-After` 指定的时刻，或无有效头的该次 429 时间加 30 秒。因此后续 429 只能延长或维持冷却，不能缩短已有冷却。

**状态来源展示：**每行状态码旁显示“刚刚检查”或“缓存”。“刚刚检查”的 Tooltip 显示“检查于 {时间}”；“缓存”的 Tooltip 显示“检查于 {时间} · 有效至 {时间}”。用户强制 Refresh 期间保留旧状态，并在状态旁显示“上次结果 · 正在刷新”；本轮获得最终响应后替换状态并标记“刚刚检查”。429/未完成时若当前界面已有旧状态，保留其状态码并标为“上次结果”，Tooltip 显示原检查时间；即使已超过 5 分钟也只作为历史结果留在当前界面，不续期、不写回有效缓存，关闭/重开或恢复过期快照时必须过滤。当前界面没有旧状态时显示未检查。Images 工具栏下方显示 Origin 冷却提示：“图片服务器限制了请求。{时间}后可再次刷新该服务器的图片。”时间显示对应图片请求 Origin 的冷却截止时间。这样不会把旧状态伪装成新检查结果。

**防止旧请求覆盖新结果：**每轮刷新使用单调递增的 `runId`，同时绑定 `tabId + page URL + scan generation`。页面导航、Tab 切换、Rescan 或新一轮取代旧轮时递增/失效令牌。响应提交 UI 或缓存前必须同时通过 `runId`、Tab、页面 URL、generation 检查；旧请求只能结束自身，不得覆盖新状态。UI 状态与缓存写入都要有该校验；仅在页面仍匹配时写入对应扫描快照。

### 当前行为与候选改动边界

当前实现按最多 6 个 URL 分批调用注入脚本，各批串行；每批最多 2 个请求并发，请求间隔 250ms，单请求超时 8 秒。429 会停止该图片请求 Origin 的本轮后续项，但尚在途请求允许完成；被跳过项可能写成未检查。下一次不处于冷却期的手动刷新会重新请求当前筛选范围。重复点击在当前一轮未结束时被阻止。现有页面快照最多保留 10 分钟，但其中图片状态没有独立的 5 分钟 TTL 校验；当前没有这项状态缓存和 `Retry-After` 冷却实现。

最小方案不提高并发、不自动重试 429。可在保留 2 并发和 Origin 限流保护的前提下，复用有效成功检查结果以加快普通重开；强制 Refresh 仍重新检查。是否调整 250ms 间隔或每批数量不属于已确认决策，须通过有界测试证明不会提高 429 后另行评估。

## 4. 预计测试与回归影响

### 定向测试

1. 解析后主机名为 `bat.bing.com` 且路径精确为 `/action/0` 时排除；验证带 Query、带 Fragment 仍排除；`/action/0/`、大小写不同路径、其他主机同路径、同域其他路径、普通第三方图片和普通带 Query 图片均保留；Alt 数据与 Audit 统计不受其他图片变化影响。
2. 同一轮重复 URL 只产生一次请求，所有重复行获得同一结果；峰值并发始终不超过 2。
3. 页面 Origin 与图片请求 Origin 不同时，缓存按页面 Origin + 图片 URL 隔离，冷却按图片请求 Origin 隔离；切换页面 Origin 不串用缓存，但同一图片请求 Origin 的冷却仍生效。
4. 页面快照仍在 10 分钟保留期内、图片状态却已超过 5 分钟时，读取时过滤过期状态；没有 `checkedAt` 的旧 `imageStatuses` 不作为有效缓存恢复。
5. 有效缓存普通重开可复用；到 5 分钟边界前有效，过期后不复用；读取不延长 TTL；会话重启/扩展重载后缓存不可用。手动 Refresh 无论缓存是否有效都重新请求。
6. 新取得的 404/500 替换旧 200；无可判定最终 HTTP 响应时不覆盖尚有效缓存。HEAD 405/501 后回退 GET，只缓存 GET 最终结果；GET 无法取得最终响应时不缓存 HEAD 或 GET 的失败状态。
7. `Retry-After` 秒数和 HTTP-date 均得到正确冷却截止时间；无效、缺失或因 CORS 无法读取时，从收到 429 起按图片请求 Origin 冷却 30 秒。冷却内不自动请求或手动请求该 Origin，冷却后手动刷新可请求。
8. HEAD 405/501 回退 GET；验证 GET 最终 200、404，以及 GET 超时/网络失败的缓存与状态处理。
9. 429 到达时保留此前已成功状态，并标为上次结果；即使旧状态已超过 5 分钟，也只允许在当前界面作为历史结果保留，不得续期或从过期快照恢复。没有旧状态的未完成项保持未检查。UI 分别显示“刚刚检查”“缓存”“上次结果 · 正在刷新”和精确 Tooltip；工具栏下方冷却提示显示正确图片请求 Origin 与截止时间。
10. 同 Origin 多个请求同时返回 429 时，不再启动该 Origin 的新请求，已发出的请求允许完成，冷却截止时间不被后续响应缩短；混合 Origin 队列继续处理其他 Origin，且全局峰值并发不超过 2。
11. 用户快速切页、Rescan、重复 Refresh 时，旧异步响应不能覆盖当前 Tab、URL、generation 或 runId 的新结果；同一轮重复图片 URL 仍仅请求一次。

### 回归范围与潜在影响

- **Images：**图片总数、排除数、Alt 缺失/空值统计、筛选、CSV 导出、Status 文案和进度。
- **跨页面状态：**不同 Tab、同 Origin 页面切换、导航、Popup 关闭/重开、Rescan、扩展会话缓存清除。
- **评分规则：**Bing 端点不再进入图片数据后，可能减少由该单一行导致的图片 Alt Issue/指标；其他图片保持原逻辑。不得改评分权重或其他规则。
- **网络保护：**并发上限固定为 2；429 不自动重试；冷却需防止用户点击造成对同一 Origin 的额外请求。
